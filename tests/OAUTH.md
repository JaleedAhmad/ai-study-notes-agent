# Batch 4A: GitHub OAuth investigation and security contracts

Tests and investigation only, on the existing development working tree after
Batch 3B. Production, dependencies, schema, deployment, and existing authorization
tests are unchanged. No credentials, user data, live OAuth, or external services
were used. This document does not select or implement a schema design.

### Failure, cancellation, replay and concurrency

- Non-200 token/email replies and missing tokens return None; the UI does not
  authenticate. Database lookup/insert failures also leave identity unset.
- Network errors and malformed token/email replies can raise before the callback's
  database try/except. The real outer application boundary catches them and stops
  rendering, without authentication, but leaves callback parameters in the URL.
- `error=access_denied` without code is ignored; cancellation parameters remain.
- An already authenticated session skips code exchange. That is not a consumed
  state check: resetting identity/logging out allows the same callback to reach
  the provider again. Clearing browser parameters does not invalidate a copied URL.
- There is no consume-before-exchange step. A synthetic reentrant callback during
  an in-flight exchange reaches the provider twice. Real Streamlit scheduling and
  deployed multi-worker concurrency were not exercised.
- The fixtures intentionally allow repeated code exchange to reveal the local
  check ordering. They do not claim GitHub accepts real reused authorization codes.

### Isolation and results

The real authorization URL, callback, provider helper, account resolution and
identity gate execute. HTTP endpoints return raw synthetic responses: they do
not check state, consume codes, remove unverified emails, or bind subjects. A
profile response exists in the fixture only if production requests it. The real
database functions use the existing query-evaluating memory store, with no RLS
or subject mapping supplied by the fake. New state is not injected into production
session storage by the tests.

Error tests execute the real application's outer exception boundary with rendering
stubbed out; they do not silently catch arbitrary exceptions in the test body.
The concurrency case is deterministic reentrancy, not a live browser/thread test.
All network and filesystem safeguards remain active.

## Confirmed behavior versus unverified risks

Confirmed: fixed state and missing local binding/expiry/consumption; ignored email
verification; no stable provider ID retrieval/storage; missing explicit timeouts;
incomplete cancellation/error cleanup. Mocked verified-email selection can create
the wrong new local account when an unverified primary precedes a verified email.

Unverified: live login-CSRF/account-takeover exploitability, GitHub eligibility for
particular email arrangements, real code reuse, provider API availability,
cookie/session survival across navigation, multi-worker races, and deployed RLS.
Malformed-token/profile cases are defensive input contracts, not claims GitHub
normally emits those malformed responses. Different-subject/same-email responses
are synthetic identity-design probes, not evidence GitHub simultaneously grants
the same verified email to two accounts.

## State storage and navigation decisions for Batch 4B

There is no current state stored in Streamlit, cookies, local files, or database
code. The plain anchor performs external navigation. Local source cannot prove
whether the callback returns to the same Streamlit server session behind the
actual host/proxy. Pure in-memory session state must not be assumed to survive.

Smallest conditional option: random pending attempts in server-held Streamlit
state, with expiry and single-use consumption, ONLY if the real round-trip binding
is verified for the chosen runtime. Missing state must fail closed; never fall
back to accepting an unsigned/unbound callback to restore compatibility.

More robust option: a small OAuth initiation/callback component with a securely
scoped browser correlation cookie and a short-lived server-side attempt store.
Cookie flags/origins must fit actual hosting. A single-worker store may be enough
only under an explicit single-worker deployment; replicas need shared atomic
consumption. A signed state alone is not browser binding. IP addresses or query
parameters alone are not substitutes for independent browser correlation.

Initiate attempts deliberately; do not rotate one pending nonce on every unrelated
form rerender. Choose an explicit bounded multi-tab policy. Consume the matched
attempt before exchange, including failed exchange/cancellation handling; do not
consume another attempt merely because an invalid callback arrives. Handle
provider errors, clear callback parameters, and bound HTTP requests. Restart or
expiry can safely require starting login again.

If a browser binding cannot be implemented and verified, temporarily disabling
GitHub login is the fail-closed option, with explicit approval and recovery plans
for GitHub-only users. It is not equivalent to preserving legitimate OAuth login.

## Stable subject: schema and migration options (no selection made)

State/email/parser repairs need no user-schema migration, but leaving email as
the sole local identity key is not a complete stable-subject repair. A durable
mapping is needed to preserve existing custom UUIDs across provider email changes.
No such mapping is used by current code; deployed extra columns are unverified.

| Option | Impact / tradeoff |
| --- | --- |
| Nullable provider-subject column plus unique `(provider, subject)` constraint | Smallest additive relational option for one identity per user. Preserve users.id and session foreign keys. Requires approved DDL, uniqueness, backfill, conflict handling, and rollback. |
| Separate identity table mapping `(provider, subject)` to users.id | Preserves UUIDs and supports explicit multiple identities later, but adds a table/repository operations. Also needs approved migration and recovery rules. |
| Subject-derived UUID for new users | Can avoid a new column for new accounts, but legacy random UUIDs do not match; existing sessions and unique email conflicts still need a migration/mapping policy. Not a seamless fix. |
| Durable sidecar mapping | Avoids user-table DDL but adds another data store with backup, concurrency, deployment and recovery requirements. Usually more disruptive here. |

Encoding subjects inside provider/email fields is a semantic data migration,
breaks exact `provider == github` compatibility, and lacks the required unique
subject constraint. It is not a safe migration-free shortcut.

Legacy GitHub users have no independently recorded subject. Automatically binding
the first current verified email claimant to a historical UUID cannot establish
historical account ownership. Approve trusted backfill/recovery evidence, ambiguous
record quarantine, and conflict rules before binding legacy accounts. Never merge
password accounts by matching email. New subject bindings must be unique under
concurrent account creation. After binding, subject controls identity; email is
verified contact metadata, and email collisions must not merge user accounts.

Approval is needed for persistent mapping design, legacy proof/recovery, email
collision/update behavior, and browser-binding/deployment assumptions. Schema
changes or provider migration have not been chosen or performed. A staged 4B can
repair state/verification/transport first, but must not claim complete identity
security while durable subject binding remains unresolved.

## Batch 3B compatibility and rollback considerations

Keep literal provider `github` separate from random OAuth state. Current callback
uses state both for routing and `authenticate_oauth_user(email, state)`; merely
randomizing the URL would cause all valid callbacks to fail the provider checks.

A structured provider identity requires corresponding callback/account-resolution
adapters; the existing helper returns only email, while local authentication must
continue returning `(bool, validated local UUID or public error)`. The browser
must never set a provider ID as the application's local UUID. Unknown callback
errors and database failures must preserve logged-out state.

Batch 3B intentionally refuses password/mixed-provider linking and normalizes
creation races to failure. Preserve those contracts. Legitimate existing GitHub
users pass today's offline success test, but preserving them securely after subject
binding requires the approved migration/recovery policy; tests cannot create that
historical evidence. Restrict GitHub login rather than roll back to unsafe linking
if a rollout fails. No Batch 4B fixes are implemented here.
